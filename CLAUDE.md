Design a low chip count Z80 based computer on a breadboard using a atemega1284p as video controller, rom emulator and uart
- 16MHz master clock
- divide by 2 to get 8MHz Z80 CPU clock
- Z80 has 128K SRAM attached with A16 tied low so its a full 64K. The idea is that when the Z80 boots it sees a rom (which will be emulated by the 1284p). It can read from the ROM and write to the full 64K of SRAM. There is an external latch bit that can be toggled via an IO port write. This mode control bit stars off as 0 which means "read from rom, write to sram". When this mode control is flipped to 1 it is "read from sram, write to sram". ie. the rom is no longer used. This means the roms main job at startup is to copy itself into the sram, then flip the mode control to 1.
- 16MHZ clock also drives the 1284p
- 1284p has 32 IO pins in four 8 bit ports. One 8 bit port goes to a 74LS373 latch (input side). The output side goes to the Z80 data bus. 14 IO pins go to the A0 to A13 pins of the Z80. The 1284p controls _RESET on the Z80 and on startup the 1284p starts up and holds the Z80 in reset. The _MREQ, _IORQ, _RD and _WR lines from the Z80, as well as _BUSRQ. Two IO pins are configured as a UART. Another 2 IO pins are used for HSYNC and VSYNC outputs
- timers are used to generated HSYNC pulse every 64us. And a VSYNC pulse at 50Hz (PAL timing).
- At reset the the 1284p goes into monitor mode. An external system communicates with the uart and has a simple terminal command line interface to allow a user to read/write to the 16K RAM in the 1284p as well as upload a file into it using xmodem (assumption is that only 8K is used for rom emulation space). Once the user has uploaded the rom content via xmodem, they give a command to 'start rom emulation'. (Addendum, 2026-09-11: the 1284p also samples a boot-mode strap on the RXD pin once at reset — a permanent ~3.3k pull-down to GND, only effective when no serial adapter is connected. Strapped low ⇒ it copies a flash-resident copy of the CP/M `stage1.bin` into the ROM-emulation buffer and starts the Z80 directly, no host needed; adapter connected or strap high ⇒ monitor mode as above. See `docs/pin-map.md` PD0 and `firmware/avr-1284p/src/monitor.c`.) The 1284p releases reset on the z80 and it starts up. ROM requests will appear as _MREQ and _RD going low. A flip flop will clock that and immediately drive _WAIT low on the z80. The 1284p will have the 14 address lines as inputs. The 1284p will be in a tight assembly loop monitoring _MREQ and _RD and once it does, it reads the 14 address pins (at this stage it does not matter what the two high address pins are). It looks up the appropriate byte in the 1284p's internal RAM (which will have the rom image uploaded via xmodem). It switches the IO pins used for the databus to outputs. The 74LS373 is a transparent latch so the data will flow through to the z80. The 1284p will pause for one or two nops then trigger the _WAIT control flip flop to through _WAIT high. The data will be latched in the 74LS373 somehow and the tristate outputs of the 74LS373 will be controlled by _RD and the mode control bit thorugh a few gates. This way the databus will go tristate immediately when _RD goes high (rather than much longer if the 1284p tried to do it). The 1284p puts the IO pins used for the data bus back in input mode and goes back into the tight loop waiting for the next memory request. The z80 code being executed is effectively copying data from rom to the z80 attached sram. Once this copy is done, the z80 prepares itself to execute to run from sram, then flips the mode control bit to 1 so that subsequent reads come from sram. The 1284p needs to sense this mode change as well. Rather than needing more logic, the 1284p could have a magic ram location that if read from flips it out of rom emulation mode.
- Once the 1284p has exited rom emulation mode, it goes in to video generation mode. The timers are controlling HSYNC and VSYNC. The graphics will be 640x200 two color on a PAL screen of 312 lines. When the scanline gets to the first of the 200 lines just after the HSYNC at the beginning of the scanline, the 1284p asserts _BUSRQ to stop the Z80 and tristate its bus. The 1284p then waits a few microseconds, put the 14 address lines as outputs and controls _MREQ and _RD to to start reading 80 consecutive addresses from the external sram. Each 500ns apart. When each byte is fetched the 1284p does not read the databyte from the sram . Instead it is latched into a 74ls166 shift register being clocked at 16Mhz to generate the pixel stream. The 1284p might need tight assembly code that 'waits for hysnc' in order to concisely align execution with the hsync pulse. After the 80 address increments, the 1284p stops any changes on the address bus and releases _BUSRQ. The z80 keeps going for a few microseconds. Meanwhile, the 1284p waits for the next HSYNC and does the same process again for the next 80 bytes. Note, that we could just tie A15 and A14 high via pullups so that the 16K that that the 14 address lines off the 1284p end up controlling the 0xc000 to 0xffff region (remember it is doing the increments when the z80 has tristated a lot of signals). The 1284p does 200 lines like this. After the end of the 200th line, the 1284p releases _BUSRQ and just waits for the the 1st line of the next frame. Meanwhile the z80 gets time to execute some programs.
- Ideally, I want the 1284p to act as a uart for the z80 as well (an emulated uart), but that might be quite hard. The use of the 74ls373 means that we can only read data from the 1284p. One way of handling writes would be have the 1284p monitoring _IORQ and then do a IO read instruction that puts a 16 bit IO address out. Eight of the address bits could be used as the write value (eg. if we had a 74ls138 decoding the IO space using A8-A10, then use A0-A7 as a write value. This means you would not be allowed to use IO instructions that only use the lower 8 address lines. But the bigger problem is timing. During video generation the z80 is mostly paused. During the 112 spare lines it can do stuff, so the 1284p could monitor _IORQ during those 112 blank lines and respond to reads in a similar way to how the rom emulation worked. So the real uart in the 1284p would receive bytes, and then the received byte would be virtualised so that the z80 could read it with an IO instruction. A z80 write of a byte of serial data would be the reverse, but as mentioned the byte to write would end up on the lower address lines. This could be an OUT instruction. With the 74ls373 forced to stay in tristate, the data byte on the z80 data bus at the time of the write would be ignored and simply the address lines would be read to get that byte.
